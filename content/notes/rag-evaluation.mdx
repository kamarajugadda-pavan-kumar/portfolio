Every RAG tutorial ends at "it's working!" but the hard part is knowing *how well* it's working — and catching regressions when you change your chunking strategy, swap your embedding model, or upgrade your LLM.

This post is about practical RAG evaluation: what metrics matter, how to build a golden dataset efficiently, and how to avoid the trap of using GPT-4 as a judge for every single query.

## The Evaluation Stack

A useful RAG eval stack has three tiers:

| Tier | Metrics | Cost | Cadence |
|---|---|---|---|
| 1. Retrieval | Precision@K, Recall@K, MRR | Free | Every commit |
| 2. Answer quality | BERTScore, ROUGE-L | Low | Daily |
| 3. Qualitative | LLM-as-judge faithfulness | Medium | Weekly |

The mistake most teams make: jumping straight to tier 3 for everything. LLM judge calls at $0.01–0.05 each add up fast when you're evaluating 500 queries.

## Building a Golden Dataset

A golden dataset is a set of (query, expected_answer, relevant_doc_ids) triples. It's the foundation of everything.

**The fast way to build one:**

1. Sample 200 queries from your real production logs (or anticipated queries)
2. Run your RAG system on each query, get the answer
3. Have a human (or GPT-4 in a careful prompting setup) mark: (a) which retrieved docs are relevant, (b) whether the answer is correct
4. Store as structured JSON

```python
from pydantic import BaseModel

class GoldenExample(BaseModel):
    query: str
    expected_answer: str
    relevant_doc_ids: list[str]
    answer_keywords: list[str]  # for keyword-based answer checking
    difficulty: Literal["easy", "medium", "hard"]

def create_golden_example_from_log(log_entry: dict) -> GoldenExample:
    # Use GPT-4 to assist with labelling
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": ANNOTATION_PROMPT},
            {"role": "user", "content": json.dumps(log_entry)},
        ],
        response_format={"type": "json_object"},
    )
    return GoldenExample(**json.loads(response.choices[0].message.content))
```

Build the golden dataset once. Maintain it. Add to it when you find failure modes. Never regenerate it from scratch.

## Tier 1: Retrieval Metrics (Free)

These are computed from your golden dataset without any LLM calls:

```python
def evaluate_retrieval(
    retriever: BaseRetriever,
    golden: list[GoldenExample],
    k: int = 5,
) -> dict[str, float]:
    precisions, recalls, mrrs = [], [], []

    for ex in golden:
        retrieved = retriever.retrieve(ex.query)
        retrieved_ids = [n.node_id for n in retrieved[:k]]
        relevant = set(ex.relevant_doc_ids)

        tp = len(set(retrieved_ids) & relevant)
        precisions.append(tp / k)
        recalls.append(tp / len(relevant) if relevant else 0)

        mrr_score = 0.0
        for rank, doc_id in enumerate(retrieved_ids, 1):
            if doc_id in relevant:
                mrr_score = 1.0 / rank
                break
        mrrs.append(mrr_score)

    return {
        "precision@k": sum(precisions) / len(precisions),
        "recall@k": sum(recalls) / len(recalls),
        "mrr": sum(mrrs) / len(mrrs),
    }
```

Run this on every commit. A drop in MRR > 2 points is a regression signal.

## Tier 2: Answer Quality (Low Cost)

BERTScore computes semantic similarity between generated and expected answers using contextual embeddings. It runs locally (no API calls):

```python
from bert_score import score as bert_score

def evaluate_answer_quality(
    pipeline: RAGPipeline,
    golden: list[GoldenExample],
) -> dict[str, float]:
    generated = [pipeline.query(ex.query) for ex in golden]
    references = [ex.expected_answer for ex in golden]

    P, R, F1 = bert_score(generated, references, lang="en", verbose=False)
    return {
        "bertscore_precision": P.mean().item(),
        "bertscore_recall": R.mean().item(),
        "bertscore_f1": F1.mean().item(),
    }
```

## Tier 3: Faithfulness (Selective)

Faithfulness — does the answer make claims supported by the retrieved context? — requires either an NLI model or an LLM judge. Use it selectively:

```python
def check_faithfulness_sample(
    pipeline: RAGPipeline,
    golden: list[GoldenExample],
    sample_size: int = 50,
) -> float:
    """Run faithfulness eval on a random sample to control costs."""
    sample = random.sample(golden, min(sample_size, len(golden)))
    scores = []

    for ex in sample:
        result = pipeline.query_with_context(ex.query)
        score = faithfulness_judge(
            answer=result.answer,
            context=result.retrieved_context,
        )
        scores.append(score)

    return sum(scores) / len(scores)
```

Run this weekly on a 50-query sample rather than daily on 500 queries. It costs ~$0.50/week instead of $25/week.

## Tracking Metric Drift

Store eval results in SQLite with a timestamp. Plot weekly.

```python
def record_eval_run(metrics: dict[str, float], db_path: str = "eval.db") -> None:
    with sqlite3.connect(db_path) as conn:
        conn.execute("""
            CREATE TABLE IF NOT EXISTS eval_runs (
                id INTEGER PRIMARY KEY,
                timestamp TEXT,
                mrr REAL,
                precision_at_5 REAL,
                bertscore_f1 REAL,
                faithfulness REAL
            )
        """)
        conn.execute(
            "INSERT INTO eval_runs VALUES (NULL, ?, ?, ?, ?, ?)",
            (
                datetime.utcnow().isoformat(),
                metrics.get("mrr"),
                metrics.get("precision@k"),
                metrics.get("bertscore_f1"),
                metrics.get("faithfulness"),
            ),
        )
```

## The Key Takeaway

A RAG system without evaluation is a guess. The minimum viable eval setup is:

1. A golden dataset of 100+ (query, answer, relevant_doc_ids) triples — takes one weekend
2. MRR and precision@5 computed on every change — free, fast, catches regressions
3. BERTScore for answer quality — runs locally, run daily
4. LLM faithfulness judge on a 50-query weekly sample — costs ~$2/month

That's a meaningful signal for essentially zero ongoing cost. There's no excuse not to have it.
