## Overview

Manual job searching is a repetitive, high-friction workflow: search → filter → read JD → assess fit → apply → track. I built this tool to automate the entire pipeline using a multi-agent LangGraph graph, with Playwright handling browser-level interactions and SQLite maintaining persistent state across runs.

<Callout type="tip">
  The key insight: each "agent" in the graph is a narrowly scoped node with
  clear input/output contracts. This makes the graph composable, testable, and
  easy to extend with new job boards.
</Callout>

## Problem

Job searching at scale requires:

- Visiting 5–8 job boards daily
- Manually filtering hundreds of listings based on role, stack, and location criteria
- Reading full JDs to assess fit before applying
- Tracking application status without duplicate applications

No existing tool handled all of these without significant manual intervention.

### Graph Nodes

The LangGraph StateGraph has five nodes wired in sequence with conditional edges:

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated
import operator

class JobSearchState(TypedDict):
    query: str
    raw_listings: Annotated[list[dict], operator.add]
    scored_listings: list[dict]
    applied: list[str]
    errors: list[str]

graph = StateGraph(JobSearchState)
graph.add_node("search", search_node)
graph.add_node("deduplicate", dedup_node)
graph.add_node("score", score_node)
graph.add_node("apply", apply_node)
graph.add_node("persist", persist_node)

graph.set_entry_point("search")
graph.add_edge("search", "deduplicate")
graph.add_edge("deduplicate", "score")
graph.add_conditional_edges(
    "score",
    lambda s: "apply" if s["scored_listings"] else END,
)
graph.add_edge("apply", "persist")
graph.add_edge("persist", END)
```

### Browser Automation with Playwright

The `search_node` and `apply_node` use async Playwright with a persistent browser context to maintain session state across job board visits:

```python
async def search_node(state: JobSearchState) -> dict:
    async with async_playwright() as pw:
        browser = await pw.chromium.launch_persistent_context(
            user_data_dir="./browser_data",
            headless=True,
        )
        page = await browser.new_page()
        listings = []

        for board in JOB_BOARDS:
            await page.goto(board.search_url(state["query"]))
            await page.wait_for_load_state("networkidle")
            listings.extend(await board.extract_listings(page))

        await browser.close()

    return {"raw_listings": listings}
```

### LLM-based Relevance Scoring

The `score_node` sends each JD to GPT-4o-mini with a structured output schema:

```python
from pydantic import BaseModel

class JobScore(BaseModel):
    relevance_score: float  # 0-1
    stack_match: list[str]
    stack_gap: list[str]
    rationale: str
    apply: bool

async def score_node(state: JobSearchState) -> dict:
    scored = []
    for listing in state["raw_listings"]:
        response = await client.beta.chat.completions.parse(
            model="gpt-4o-mini",
            messages=[
                {"role": "system", "content": SCORING_PROMPT},
                {"role": "user", "content": listing["full_jd"]},
            ],
            response_format=JobScore,
        )
        score = response.choices[0].message.parsed
        scored.append({**listing, "score": score.model_dump()})

    return {"scored_listings": [s for s in scored if s["score"]["apply"]]}
```

### Persistent State with SQLite

SQLite tracks applied jobs, preventing duplicate applications across runs:

```python
import sqlite3
from contextlib import contextmanager

@contextmanager
def get_db():
    conn = sqlite3.connect("jobs.db", check_same_thread=False)
    conn.row_factory = sqlite3.Row
    try:
        yield conn
    finally:
        conn.close()

def is_duplicate(job_id: str) -> bool:
    with get_db() as conn:
        row = conn.execute(
            "SELECT 1 FROM applications WHERE job_id = ?", (job_id,)
        ).fetchone()
        return row is not None
```

## Key Design Decisions

<Steps>
  <Step title="LangGraph over raw LangChain agents">
    LangGraph's explicit state machine model gave us predictable error recovery
    — when the `apply_node` fails on a specific listing, the graph logs the
    error to `state.errors` and continues rather than halting the entire run.
  </Step>
  <Step title="Persistent browser context">
    Using Playwright's `launch_persistent_context` instead of a fresh browser
    per run maintains cookies and session state, avoiding repeated CAPTCHA
    challenges on job boards that rate-limit headless browsers.
  </Step>
  <Step title="SQLite over Redis for deduplication">
    For a single-user tool running locally, SQLite's zero-infra footprint beats
    Redis. The application table is indexed on `job_id` (a hash of title +
    company + URL), making duplicate checks sub-millisecond.
  </Step>
  <Step title="Structured output for scoring">
    Using `response_format=JobScore` (Pydantic model) with GPT-4o-mini
    guarantees machine-readable scores without prompt engineering fragility. The
    `apply: bool` field is the only gate to the apply node.
  </Step>
</Steps>

## Results

- **~80% reduction** in time spent on manual job searching
- Processes 200+ listings per day across 5 job boards
- < 5% duplicate application rate (down from ~15% with manual tracking)
- Relevance filter reduces false positives: 94% of auto-applied jobs were genuinely good fits (validated manually on a 50-job sample)

## What I'd Do Differently

1. **Add a human-in-the-loop review step** before the apply node — the current flow is fully autonomous which occasionally applies to borderline-fit roles.
2. **Replace SQLite with a proper ORM** (SQLModel) as the schema has grown past 5 tables.
3. **Instrument with LangSmith** from day one — debugging graph execution without traces was painful.
4. **Cache JD embeddings** for semantic deduplication — currently deduplication is string-hash-based, missing near-duplicate listings across boards.
