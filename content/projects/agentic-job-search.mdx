## Overview

Job searching at scale is a repetitive grind: find career pages, figure out how each one paginates, manually read hundreds of job descriptions, assess fit, apply, and somehow avoid double-applying. I built this tool to own the entire pipeline — from discovering listings on an arbitrary company career page to submitting applications — with a human approval gate before anything is sent.

<Callout type="tip">
  The scraper generates itself. Rather than hard-coding parsers per site, a
  vision LLM analyzes a screenshot and live HTML of the careers page, extracts
  CSS selectors or intercepts the underlying jobs API, then generates a
  site-specific scraper script on the fly. New company = zero manual work.
</Callout>

## Problem

Every step of job searching that could be automated wasn't:

- Career pages have wildly different structures — ATS portals, custom SPAs, API-backed widgets — with no standard to target
- Pagination patterns vary: numbered pages, load-more buttons, infinite scroll, URL parameters with irregular increments
- Reading 200 JDs to find 10 good fits is pure signal extraction — exactly what LLMs are built for
- Manually tracking which jobs you've already applied to across five boards is error-prone
- Existing tools either scraped only a handful of fixed sites or required per-site configuration upfront

### Adaptive Scraper

The scraper is the most technically interesting piece. When given a company careers URL, it opens the page with Playwright and listens on the network layer first: if any XHR or fetch response contains a JSON structure that looks like a job listing (identified by key heuristics — fields like `jobTitle`, `requisitionId`, `jobCode`), the scraper locks onto that API endpoint directly and bypasses DOM parsing entirely. This is the fast path and works for most modern ATS platforms.

When no API is intercepted, it falls back to DOM mode. A compact skeleton of the page's HTML tree is built (scripts and styles stripped, tag names with IDs and classes only), then fed alongside a screenshot to a vision LLM. The LLM identifies the container element wrapping the job cards and returns a CSS selector. A second LLM pass then extracts the fine-grained selectors for titles, links, and location within each card.

Pagination is handled by a dedicated Playwright probe that runs on the live page before the screenshot is taken, checking for load-more buttons, numbered nav elements, and Next links. The href of the Next button, when found, is parsed to extract the URL parameter name and per-page step size — so the scraper knows to increment `?startrow=` by 875 or `?page=` by 1 without any manual configuration.

### Description Fetcher

Once listings are in the database (title, company, URL), a separate async pipeline opens each job detail URL with Playwright, extracts the full description text, and stores it for the evaluation stage. It runs with configurable concurrency and supports retry-on-failure for transient page load errors.

### 4-Layer Evaluation Pipeline

Rather than sending every job description to an expensive LLM call, the pipeline gates jobs through progressively costlier filters:

**Layer 1 — Rule-based filter:** Instant, zero-cost checks against the candidate's preferences loaded from a YAML profile. Title keywords, work mode (remote/hybrid/onsite), hard deal-breakers, and salary range. Anything that fails here is eliminated without touching an API.

**Layer 2 — Skill overlap gate:** Jaccard similarity between the candidate's skill set and the skills mentioned in the job description, using a normalised skills dictionary. Also free of API calls. Jobs below the configurable overlap threshold (default 30%) are eliminated.

**Layer 3 — Embedding similarity filter:** The full job text and a condensed candidate profile are embedded using OpenAI's embedding API and compared via cosine similarity. One cheap API call per job. This catches semantic fit that keyword matching misses — a job posting "machine learning" when the candidate lists "ML" — and eliminates borderline matches before the expensive step.

**Layer 4 — AI rubric scorer:** Jobs that reach here are scored across five dimensions by a structured-output LLM call: skills match, experience alignment, role growth, work preference match, and seniority fit. The model returns a numeric score per dimension plus a one-line summary and a `Strong Match / Possible / Weak Match` recommendation. Only jobs above the configurable threshold (default 65) are marked for application.

### LangGraph Apply Graph with Human-in-the-Loop

The application workflow is a three-node LangGraph `StateGraph`: `build_resume → analyse_form → submit`. It is compiled with a `SqliteSaver` checkpointer (the same SQLite database used throughout) and `interrupt_before=["submit"]`.

When `job-agent apply <job_id>` is run, the graph runs through resume generation and form analysis, then pauses. The candidate reviews everything. Running `job-agent approve <job_id>` resumes the same graph thread from the checkpoint and submits. This means the state — form field mappings, proposed values, resume path — is durably saved between the two CLI calls, not held in memory.

### CLI and Dashboard

The `typer`-powered CLI exposes every stage as a named command: `init`, `scrape`, `fetch-descriptions`, `evaluate`, `scores`, `apply`, `approve`, and `dashboard`. The `scores` command renders a Rich table of evaluated jobs ranked by match score, filterable by recommendation tier. The `dashboard` command opens a full TUI built with Textual.

### Provider-Agnostic LLM Configuration

Every LLM call is routed through a factory that reads `config.yaml` at runtime. Each role — `analyst`, `script_writer`, `matcher`, `description`, `evaluator` — has its own provider, model, temperature, and token settings. Swapping the evaluator from GPT-4o-mini to DeepSeek is a one-line config change with no code touched. Vision-capable models are required for the analyst and script_writer roles; text-only models are fine for the rest.

## Key Design Decisions

<Steps>
  <Step title="API interception before DOM parsing">
    Checking the network layer first turns a hard scraping problem (parse an
    arbitrary SPA) into a simple REST call. Most modern ATS platforms
    (Greenhouse, Lever, Workday, custom) expose a JSON endpoint that the page
    itself calls. Intercepting it gives structured data without selector
    fragility.
  </Step>
  <Step title="4-layer funnel to minimise API spend">
    Layer 4 (AI rubric) is the only step that costs meaningful money. Running
    200 jobs through it directly would be wasteful and slow. The three upstream
    layers eliminate 60–80% of jobs at zero or near-zero cost, so only the
    genuinely plausible candidates ever reach the LLM scorer.
  </Step>
  <Step title="SqliteSaver checkpointer for apply state">
    Using LangGraph's built-in SQLite checkpointer means the human review pause
    is durable across process restarts. The candidate can run `apply`, close
    their laptop, and `approve` hours later. There is no in-memory state to
    lose.
  </Step>
  <Step title="YAML-driven candidate profile">
    Separating candidate data (skills, preferences, experience, deal-breakers)
    into a structured YAML file keeps the evaluation logic generic. Changing
    target roles or adding a skill requires editing a config file, not modifying
    any pipeline code.
  </Step>
</Steps>

## Results

- **Layer 1–3 filters eliminate ~70% of jobs** before a single expensive API call is made
- Scraper handles arbitrary career pages without per-site configuration — tested across Greenhouse, Lever, Workday, Oracle HCM, and custom SPAs
- Pagination auto-detection correctly handles URL parameter steps as irregular as 875 items per page
- 4-layer evaluation reduces LLM API cost by roughly 5× compared to evaluating every job directly
- Human-in-the-loop checkpoint prevents any unreviewed application from being submitted

## What I'd Do Differently

1. **Build the discovery graph first** — the `discover` command (scrape all configured targets on a schedule) is stubbed; in hindsight, that automated discovery loop should have been the first thing built, not the last.
2. **Add LangSmith tracing from day one** — the 4-layer pipeline has conditional exits at every layer; debugging why a specific job was eliminated at Layer 2 vs Layer 3 without traces requires log-spelunking.
3. **Cache embeddings** — Layer 3 recomputes candidate profile embeddings on every run. A simple on-disk cache would eliminate a redundant API call for the profile side.
4. **Expose a web UI instead of TUI** — the Textual dashboard works locally but can't be shared. A lightweight FastAPI + React frontend would make it easier to review scored jobs on mobile or share with others.
